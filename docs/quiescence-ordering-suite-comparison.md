# 複数開始局面 A/B 探索設定比較

## 目的

PR #136 の固定3局面カタログを、同じ探索設定境界で `baseline` と `candidate` に対して繰り返し実行し、**何が変化したか**を構造化して残す研究用CLIです。既存の `runOrderingTrial` をそのまま呼ぶため、探索エンジンや評価関数は複製・変更しません。通常のゲームUI、Worker、保存データ、CIの性能判定にも接続しません。

既定の名前付き設定は baseline=`original`、candidate=`material`（ともに静止探索追加1手、通常探索順`standard`、標準評価）です。公開APIは `SuiteComparisonConfig` で同じ `Setting` 型の別組合せも指定できます。fixed は既存の通常深さ3、timed は最大深さ4かつ各API呼出しに独立した1,000msを既存実行器どおり渡します。

## 実行

```sh
npm run measure:quiescence-ordering-suite-comparison          # timed（既定）
npm run measure:quiescence-ordering-suite-comparison -- fixed
npm run measure:quiescence-ordering-suite-comparison -- timed
```

各局面で baseline と candidate をウォームアップ3回、本測定8回ずつ同期・直列で実行します。局面順と試行順から決定する交互順序で、8回の本測定は各設定が先行する回数を4回ずつにします。各呼出しは既存実行器が独立した不変スナップショットを作るため、同じ初期局面・手番・モード・深さまたは時間制限を与えます。時計や期限を設定間で共有しません。

## 結果と数値

`runSuiteComparison()` は生の各試行、局面別 `baseline`/`candidate` 観測、差分、スイート集計を返します。`serializeSuiteComparison()` は bigintを含まないこの結果をJSON文字列にし、非有限評価値を `"Infinity"` 等の文字列へ保全します。CLIはまず人間向け集計テキスト、続けて同じ構造の `JSON` 行を出します。

形式例（数値は説明用で、実測値ではありません）:

```text
A/B 探索設定スイート比較
対象局面=3; 正常完了=3; エラー=0; 選択手変更=1
到達深さ（局面中央値の中央値）: 3→3 (差=0, 率=0%)
探索局面数（局面中央値の合計）: 1200→980 (差=-220, 率=-18.333333333333332%)
局面別の主な差分:
  rook-pawn-opening-76-34-26-84: 手=▲…→▲…; 一致=false; 評価差=0; 深さ差=0; 探索局面数差=-80; cutoff差=12; 時間差ms=-1.4
JSON {"config":{"mode":"timed"},"positions":[...],"summary":{"targetPositionCount":3,...}}
```

局面別では、最初の本測定の選択手・評価値を具体的な観測として示し、全8本測定の選択手頻度と生試行も保持します。到達深さ、探索局面数、カットオフ数、探索APIの経過時間は本測定8回の type 7 中央値です。timed の探索局面数・カットオフ数は、既存結果の全完了反復合計を使い、fixed は唯一の完了反復を使います。

スイート集計では、局面ごとの中央値から到達深さと時間の中央値、探索局面数とカットオフ数の合計を算出します。差分は `candidate - baseline`、増減率は `(candidate - baseline) / baseline * 100` です。baselineが0、欠測、または非有限値のとき増減率は `null` とし、0やInfinityに置換しません。丸めはテキスト表示の利用側に委ね、構造化データは元の数値を保持します。

## 失敗と解釈の境界

局面の生成、探索、結果検証のいずれかで失敗すると、その局面は試行済みデータとエラー文脈を残して集計対象から外します。残りの独立局面は続行し、最後にエラー数を返し、CLIは終了コード1にします。重複局面IDや不正な名前付き設定は開始前に明確に失敗します。

選択手、評価、深さ、探索量、時間の差分は観測値であり、勝者、合格/不合格、正解手、棋力、Elo、統計的有意差を判定しません。特に、**candidateの探索局面数が減ったという事実だけでは棋力向上を意味しません**。OS負荷、JIT、GC、実行順は時間制限探索に影響するため、実時間・探索量・深さをCIの性能閾値には使いません。
