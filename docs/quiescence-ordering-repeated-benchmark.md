## 統計の定義

中央値/Q1/Q3は昇順標本に対するtype7線形補間: `h=(n-1)*p`、floor/ceil間を小数部分で補間。p=0.5/0.25/0.75。IQR=Q3-Q1。最小・最大も全8標本から算出。時間増減率は`(material中央値/original中央値-1)*100`、originalが0ならnull。本表は小数2桁表示、丸め前の値を生出力に保持。各カウンタも8標本の中央値・四分位数・最小・最大を記録し、timedは最深完了反復と全完了反復合計を分離する。

## 失敗・検証・制約

- 旧単発ベンチマーク: fixed/timed各24条件、計48条件成功、終了0。新ベンチマークの実測失敗0。
- 初回fetchのSEC_E_NO_CREDENTIALSは許可された経路で再実行して解消。実装途中のlintは追加テストfixtureの型エラーで終了1、正しい型へ修正後成功。詳細な回数・コマンド・検証結果はLOG.mdに追記。
- 新規37件を含む関連5ファイル148件成功。最終`npm run check`は終了0、lockと型チェック成功、全52ファイル1561テスト成功（137.71秒）、本番build1752 modules成功（1.60秒）。既存jsdomのnavigation未実装通知は失敗と区別する。PR情報はLOG.md/PRの確定記録を参照。
- fixedの時間中央値は減少6条件・増加6条件。変化なしの訪問数や遅くなる例も全て掲載した。initial/追加1手ではウォームアップ中にも大きな時間変動が発生し、本測定がそれより遅い例もある。3回のウォームアップで安定した実行状態を保証できない。
- 実行順を均等化してもGC/JIT、OS負荷、熱/電源状態、時間経過による変動は分離しきれない。固定局面順、1台、各条件8標本の観測であり、独立プロセス反復や信頼区間・有意差推定は行わない。
- fixedは同じ通常深さの仕事量、timedは協調的期限内の完了結果で意味が異なる。訪問数減少だけから完了深さや棋力の改善は断定できない。material既定化の証拠として十分とは判断しない。original既定、静止探索既定無効、UI/Worker/評価/SEE/ルール/保存形式/依存関係は維持。CI性能ゲートは追加しない。
- 次の候補: 今回の生データを基準に、別の実行日・機器・OSで同じ条件を直列実行し、順序別と時間経過の影響を確認する。対局評価や探索最適化は別課題とする。
