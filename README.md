# SHOGI-APP

リアル調デザインの将棋盤表示と、将来のAI対局・棋譜分析・将棋研究を支えるWebプラットフォームです。

## 概要

現在は平手初期局面の高精度・リアル調将棋盤表示およびアクセシビリティ・キーボード操作基盤の実装段階です。
本黄楊彫駒の立体表現、二文字毛筆書体、本榧盤の木目・厚み・星の対称配置、およびWAI-ARIAに準拠したグリッド・roving tabindex操作を提供します。

### 実装済みの範囲
- 平手初期局面（40枚）の正確な配置
- 本黄楊（ほんつげ）調3D立体彫駒（二文字縦書き、成駒赤文字切替）
- 本榧（ほんかや）調将棋盤（天面木目、漆目罫線、木口側面ブロック、上部リムライト）
- 盤幅・盤高 3/9・6/9 対称位置（7三・4三・7六・4六）の4つの星印
- 表示専用モードでのアクセシビリティ対応（81マスの不要なTab停止ゼロ化）
- 対局・操作モードでの roving tabindex キーボード操作（矢印キー移動、Enter/Space決定）
- スクリーンリーダー対応（先手王将・後手玉将・成駒・空マスの正確なARIA読み上げ）
- **将棋ドメイン層・合法手エンジン**:
  - 盤面上の全駒（歩・香・桂・銀・金・角・飛・王/玉・成駒各種）の幾何学的利き・移動候補計算
  - 王手判定（`isKingInCheck`）および自玉の安全確認（王手放置・ピンされた駒の離脱・自殺手の禁止）
  - **一般的な詰み判定と終局処理**:
    - `isPlayerInCheck` / `hasLegalBoardMove` / `hasLegalDrop` / `hasLegalResponse` / `isCheckmate` による純粋な局面照会
    - 玉の退避、王手駒の捕獲、盤上移動・駒打ちによる合駒、成り・不成を含む全合法応手の探索
    - 通常移動・成り・突き歩・歩以外の駒打ちによる詰みを `checkmate` として終局し、勝者・敗者・最終着手を記録
    - 応手がある王手は `status: 'check'`、王手でない局面は `status: 'active'` として共通更新
    - 王手中の手番と、詰みによる勝者をステータスバッジで文字表示し、終局後の盤・駒台・成り選択を無効化
  - **千日手・連続王手の千日手**:
    - 盤上の全駒の位置・所有者・駒種・成り状態、先後別・駒種別の持ち駒枚数、次の手番がすべて一致する局面を同一局面と定義
    - 駒の個体ID、持ち駒配列の順序、手数、棋譜・反則履歴、直前手、状態・結果などのメタデータは局面比較から除外
    - 固定順の盤面配列と正規化した持ち駒枚数から `createPositionKey` が決定的な局面キーを生成し、初期局面と各合法手後の局面を小さな `positionHistory` に記録
    - 同一局面の4回目で通常の千日手を `repetition` として終局し、勝者・敗者のない無勝負として記録・表示
    - 4出現の1回目直後から4回目までに一方の全着手が王手だった場合は、`perpetual_check_repetition` による王手側の反則負けとして記録・表示
    - 通常移動と駒打ち、assist方式とstrict方式のどちらも共通終局処理を使用。外部から渡されたカスタム局面の履歴が不一致なら現在局面を新しい基準として安全に再初期化
    - 千日手成立後に先後を交代して自動的に指し直す機能は未実装（現在は一局を無勝負として終了）
  - **投了**:
    - `executeResignation` により、`active` または `check` の現在手番側が投了し、相手側を勝者とする `resignation` 結果で終局
    - 誤操作を防ぐ確認ダイアログで投了者と勝者候補を明示し、キャンセル・Escape・フォーカストラップ・キャンセル後のフォーカス復元に対応
    - 投了確定後は詰み・反則負け・千日手と同じく盤・駒台・成り選択・キーボード操作を停止し、勝者と投了者を文字で表示
    - 投了は盤面を変える着手ではないため、盤面・持ち駒・手番・手数・着手履歴・反則履歴・局面履歴を変更しない
  - **入玉宣言法**:
    - 現在手番側の玉が敵陣3段目以内に入り、王手を受けておらず、敵陣内の自駒が玉を除いて10枚以上、完了手数が500手未満であることを純粋関数で条件別に評価
    - 点数対象は宣言側の持ち駒と敵陣3段目以内の自駒のみ。飛車・角（竜・馬を含む）は5点、金・銀・桂・香・歩とその成駒は1点、玉は0点として先後対称に計算
    - 全条件を満たして31点以上なら宣言側の勝ち、24～30点なら勝者・敗者のない無勝負として一局を終了
    - 人間UIとassist方式は条件不足の宣言を安全に拒否して対局を継続し、local AI・将棋エンジン向けstrict方式は宣言失敗側の負けとして終局
    - 確認ダイアログで宣言者、入玉・非王手、敵陣内の駒数、点数、完了手数、判定、未達条件を表示し、条件不足時は確定操作を無効化
    - 宣言は着手ではないため盤面・持ち駒・手番・手数・着手履歴・最終着手・反則履歴・局面履歴を変更しない
    - 入玉宣言による無勝負後の先後交代・自動指し直しは未実装（現在は一局を無勝負として終了）
  - **500手到達時の持将棋**:
    - `moveNumber` を「次に指す手の番号」とし、完了手数 `moveNumber - 1` が500手へ到達した合法手の反映後に判定
    - 詰み、連続王手の千日手、通常の千日手が成立していなければ、双方の持将棋点数を一切問わず、勝者・敗者のない無勝負として終局
    - 500手目の指了局面が王手なら王手を開始した側を型付き状態で保持し、相手の応手後も終局させず、開始側の連続王手が途切れた合法手の反映後に持将棋を成立
    - 通常移動・成り・駒打ちを共通終局処理へ通し、終局時は専用理由を表示して盤・駒台・成り選択・投了・入玉宣言を停止
    - 現在は無勝負で一局を終了し、先後交代や自動指し直しは行わない
  - **合意による持将棋**:
    - 少なくとも一方の玉が敵陣3段目以内へ入った入玉・相入玉局面で、現在手番側が提案し、相手側が承諾または拒否する二段階フローに対応
    - 相手玉を詰ます見込みの有無は自動推測せず、両対局者の提案・承諾によって確認されたものとして扱う
    - 点数は玉を除く盤上の全自駒と持ち駒を対象とし、盤上の場所を問わず、飛車・角（竜・馬を含む）は5点、小駒とその成駒は1点として先後別に集計
    - 入玉宣言法の点数対象が「持ち駒＋敵陣3段目以内の自駒」に限られるのに対し、合意持将棋は所有する盤上の全駒＋持ち駒を数えるため、集計関数を分離して誤流用を防止
    - 双方24点以上は勝者・敗者のない「合意による持将棋・無勝負」、一方が24点未満なら点数不足側の負けとして、双方の確定点数を結果へ保持
    - 提案前のキャンセル、提案後の拒否・Escape・背景クリックでは対局を継続し、盤面・持ち駒・手番・手数・着手履歴・最終着手・反則履歴・局面履歴を変更しない
    - 承諾時も着手や反則を追加せず、終局状態と結果だけを設定。500手持将棋の連続王手待機中に成立した場合は待機状態を解除する
    - 成立後の先後交代、自動指し直し、指し直し局の持ち時間調整は未実装
  - **新しい対局**:
    - 通常の対局中、王手中、終局後のいずれからも、確認ダイアログを経て標準の平手初期局面から新しい対局を開始
    - 確定時は `createInitialBoardState()` で `BoardState` 全体を新しく生成し、40枚の初期配置、先手番、第1手、空の持ち駒・棋譜・反則履歴、初期局面1件の千日手用履歴と再生スナップショット、標準表示へ一括復帰
    - 盤上駒・持ち駒の選択、合法手候補、成り選択、各終局確認、持将棋の提案・応答・エラー、古いフォーカス要求も破棄し、前局の一時状態を引き継がない
    - 確認を開いただけでは現在局面と選択を変更せず、キャンセル・Escape・背景クリックでは完全に維持。確定時だけ初期化し、着手・反則履歴は追加しない
    - ダイアログは安全側のキャンセルへ初期フォーカスを置き、見出し・説明のARIA関連付け、フォーカストラップ、背景操作の既定動作抑止、終了後の起動ボタンへのフォーカス復元に対応
    - 成り選択、投了、入玉宣言、合意持将棋、新しい対局の確認を相互排他にし、確認中は盤・駒台・既存の対局操作を停止
  - **棋譜一覧と局面再生**:
    - `BoardState.history` の配列順に手数と既存 `notation` を表示し、通常移動、成り、不成、駒打ちを対局中に確認
    - 初期局面と各合法手の共通終局判定後に、盤、両持ち駒、次の手番、手数、状態、直前手、結果を独立した再生スナップショットとして保存
    - 棋譜行の選択、「初期局面」「前の手」「次の手」「現在局面へ戻る」で、実際の `BoardState` を巻き戻さずに過去局面を表示
    - 選択中の行を「表示中」・`aria-current="step"`、配列末尾を別の「最新」ラベルで区別し、着手追加時はページを動かさずパネル内部だけを末尾へ追従
    - 過去局面では盤・駒台と投了、入玉宣言、合意持将棋、新しい対局を読み取り専用にし、「現在局面へ戻る」後は元の対局状態を保ったまま操作を再開
    - 外部stateに再生データがない場合は現在局面だけを基準にし、存在しない過去局面を推測せず該当棋譜行を選択不可で維持
    - 詰み、投了、反則負け、千日手、500手持将棋、合意持将棋、入玉宣言の全終局結果を着手とは別の「対局結果」領域へ表示
    - 広いPC画面では盤の右側、横幅が足りない画面では盤の下へ配置し、モバイルではARIA関連付け済みのボタンで折り畳み可能
  - **バージョン付き対局記録JSONの書き出し**:
    - 固定識別子 `shogi-app-game-record` と整数の `version: 1` を持つアプリ独自形式で、平手の最新局面、着手・直前手、結果、反則、千日手判定履歴、局面再生スナップショット、500手持将棋の待機状態を保存
    - 保存用の型と純粋変換をReact UIから分離し、ISO 8601の書き出し日時を外部から渡せる決定的な整形済みJSON（UTF-8、末尾改行あり）を生成
    - v1のプレイヤー・駒種・状態・成り・反則理由・提案者などは内部ドメイン型を参照しない固定unionと明示変換で定義し、内部型へ値や項目を追加しただけでは既存v1形式を変更しない
    - 選択、ダイアログ、フォーカス、棋譜パネル開閉、再生位置、表示専用の `viewMode` を含めず、元の対局状態と可変参照を共有しない独立スナップショットとして出力
    - 過去局面の再生中も上部の「対局記録を保存」から利用でき、表示中のスナップショットではなく実際の最新 `BoardState` を保存して再生位置を維持
    - Windowsで安全なUTC日時入りファイル名、標準のBlobダウンロード、一時リンクとObject URLの後始末、成功時の支援技術向け通知と失敗時の日本語 `role="alert"` に対応
  - **バージョン付き対局記録JSONの読み込み・完全復元**:
    - アプリ独自の `shogi-app-game-record` / `version: 1` / `initialPosition: "hirate"` だけを対象にし、上部の「対局記録を読み込む」からPC・モバイルともにJSONファイルを選択可能
    - JSON解析、形式・version識別、v1スキーマ検証、意味的整合性検証、内部型への明示変換を分離し、未知キー・型外値・範囲外座標・不正な盤サイズ・重複駒ID・不正な持ち駒・矛盾した終局結果を拒否
    - 保存盤面を信用せず、平手初期局面から通常移動と駒打ちの既存合法手APIで棋譜を再実行。駒種、手番、成り・不成、捕獲、駒ID、生成棋譜表記、盤・持ち駒、直前手、千日手履歴、再生スナップショット、500手待機状態を再計算結果と照合
    - 投了、strict方式の反則負け、合意持将棋、入玉宣言など着手外の終局は、終局直前の再現局面と既存ドメイン判定に整合する場合だけ復元。着手外終局では末尾スナップショットが終局直前を表す既存仕様を維持
    - 検証成功後だけ独立した新しい `BoardState` を原子的に設定し、入力JSONと盤・持ち駒・棋譜・各履歴の可変参照を共有しない。未終局は最新局面から続行でき、終局済みは棋譜・局面再生・結果を閲覧可能
    - ファイル名、書き出し日時、着手数、終局状態を示す確認ダイアログで明示的に確定するまで現在局面を変更しない。キャンセル、Escape、背景クリック、読み取り・検証失敗でも現在局面を維持
    - ファイル上限は500手規模の再生スナップショットに余裕を持たせた32 MiB。選択前の `File.size` と解析前のUTF-8バイト数の両方で上限を確認し、不正JSON、空ファイル、別形式、未対応version、改ざんデータを日本語エラーで区別
    - KIF / KI2 / CSA / USI、v1以外のJSON、任意局面、複数対局を含むファイルは読み込み対象外
  - 成駒の移動ルール（と金・成香・成桂・成銀＝金将の動き、竜王＝飛車＋斜め1マス、竜馬＝角＋縦横1マス）
  - 行き所のない駒（`dead_piece`）の判定（1/9段目の歩・香、1/2段目・8/9段目の桂馬）
  - 指し手検証API（`validateMove`）による不正理由の詳細識別（盤外、手番違反、王手放置、自殺手等）
  - 成り・不成の選択ダイアログと、歩・香・桂の必須成り
  - **基本的な駒打ち**:
    - 持ち駒を `Piece.id` で選択し、合法な空きマスへ1枚だけ配置
    - `validateDrop` / `getLegalDropSquares` / `simulateDropSquares` / `executeDrop` による検証・候補生成・仮想盤面・局面更新
    - 先手・後手の行き所のない駒打ち、同じ筋の未成歩だけを数える二歩、駒打ち後の王手放置を拒否
    - 飛車・角・香の直線王手に対する合駒、駒打ちによる相手玉への王手に対応
    - 歩打ち後の仮想盤面と相手側の合法な盤上移動を用いた打ち歩詰め判定（`pawn_drop_mate`）
    - 通常移動と駒打ちを `kind: 'move' | 'drop'` で履歴上区別し、駒打ち棋譜を `▲5五歩打` の形式で記録
  - **公開APIの統制と低レベル盤面更新処理のカプセル化**:
    - 盤上移動は `executeMove`（および後方互換の `applyMove`）、駒打ちは `executeDrop` を外部向け着手APIとして公開。
    - 駒打ちの事前確認には `validateDrop` と `getLegalDropSquares`、王手放置判定用の仮想盤面には `simulateDropSquares` を公開。
    - 検証を通さない低レベル盤面更新関数（`internalApplyLegalMove`）は内部専用（非公開）とし、検証回避による不正手適用経路を完全排除。
  - **提案元（proposer）に応じた既定モードの自動選択**:
    - `proposer: 'human'`（または省略時）: **アシスト方式（`assist`）**（禁じ手を候補から除外・安全に拒否し対局継続）
    - `proposer: 'local_ai'` / `'shogi_engine'`: **厳格対局方式（`strict`）**（禁じ手を提案手として受け取り、盤面・手番・手数を変更せず反則負け `foul_loss` として記録）
    - `mode` が明示された場合は明示値を優先。
  - **反則履歴（`FoulRecord`）の厳密記録**:
    - 移動元に実在する駒がある場合のみ駒種を記録。移動元が空マスや盤外など特定不能な場合は `pieceType: null` を記録（架空の駒種補完を排除）。
  - **終局後の着手拒否**:
    - 終局済み（`status: 'ended'`）の局面に対する着手は、専用理由コード `game_already_ended` で安全に拒否（新規反則負けの生成や状態破壊を防止）。
  - 内部でのイミュータブルな局面更新、手番交代、手数加算、駒捕獲（成駒の成解除）、棋譜生成（`▲7六歩`等）
- Node.js 24系＋npmに統一された厳格な依存関係・ロックファイル管理とクロスプラットフォームクリーン処理

> Windows 環境（PowerShell / コマンドプロンプト）では `.nvmrc` が自動で読み込まれない場合があります。
> 必ずターミナルで `node --version` を実行し、`v24.15.0` 以上（推奨: `v24.19.0`）であることを確認してください。

## セットアップ手順

1. **Node.js バージョンの確認**
   ```bash
   node --version
   ```
   ※ 出力が `v24.15.0` 未満の場合は、Node.js 24.19.0 LTS に更新してください（nvm 等をご利用の場合は `nvm use` を実行）。

2. **npm バージョンの確認**
   ```bash
   npm --version
   ```

3. **依存パッケージのクリーンインストール**
   `package-lock.json` に基づき、厳密なインストールを実行します：
   ```bash
   npm ci
   ```

4. **一括検証（ロックファイル・型・テスト・ビルド）**
   ```bash
   npm run check
   ```

5. **開発サーバー起動**
   ローカル開発サーバー（ポート3000）を起動：
   ```bash
   npm run dev
   ```

## 依存パッケージの install script 審査（セキュリティ方針）

npm 11.17 以降のセキュアなスクリプト実行制御に準拠し、依存パッケージの install script を明示的に審査・管理しています：

- **許可・拒否の個別管理**: `package.json` の `allowScripts` フィールドで各パッケージのスクリプト実行許可（`true`）／拒否（`false`）を個別に指定します：
  - `esbuild`: `true`（Vite・テスト・ビルドに必要なバイナリインストーラー）
  - `@google/genai`: `false`（不要な no-op スクリプト）
  - `protobufjs`: `false`（非推奨警告メッセージ表示のみ）
  - `fsevents`: `false`（`fsevents@2.3.3` は pre-built の `fsevents.node` バイナリを同梱して配布しているため、`node-gyp rebuild` を拒否した状態でもモジュール読み込みが可能であり、独立した macOS CI 検証スクリプトにおいてネイティブ監視および Vite watcher の動作を継続検証しています）
- **未審査スクリプトの遮断**: `.npmrc` に `strict-allow-scripts=true` を設定しているため、`allowScripts` に記載のない未審査のスクリプトが存在する場合、`npm ci` / `npm install` はエラーとなり実行が停止します。
- **新しい依存関係追加時の運用**: 新たにパッケージを追加・更新する際は、必ず install script（`preinstall`, `install`, `postinstall`）の有無と処理内容を確認し、真にビルドや動作に不可欠なもののみを許可してください（安易に全スクリプトを許可したり `--dangerously-allow-all-scripts` を使用しないこと）。

## CI / CD
GitHub Actions（`.github/workflows/ci.yml`）により、main/master ブランチへの push、pull request、および手動実行（`workflow_dispatch`）時に、Linux（`ubuntu-latest`）および macOS（`macos-latest`）の両 OS 環境において Node.js `24.19.0` 上で以下の一貫したパイプラインが自動実行されます：
- `npm ci`（依存関係インストール・スクリプト遮断検証）
- `npm run verify:lock`（ロックファイル完全性検証・欠落集計）
- `npm run verify:macos-fsevents`（macOS環境でのみ実行: 独立した Node.js プロセスによる `fsevents` ネイティブ監視・Vite watcher 動作確認）
- `npm run lint`（TypeScript 型チェック）
- `npm test`（Vitest テストスイート）
- `npm run build`（本番ビルド）
