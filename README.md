# SHOGI-APP

リアル調デザインの将棋盤表示と、将来のAI対局・棋譜分析・将棋研究を支えるWebプラットフォームです。

## 概要

現在は平手初期局面の高精度・リアル調将棋盤表示およびアクセシビリティ・キーボード操作基盤の実装段階です。
本黄楊彫駒の立体表現、二文字毛筆書体、本榧盤の木目・厚み・星の対称配置、およびWAI-ARIAに準拠したグリッド・roving tabindex操作を提供します。

### 実装済みの範囲
- 平手初期局面（40枚）の正確な配置
- 本黄楊（ほんつげ）調3D立体彫駒（二文字縦書き、成駒赤文字切替）
- 本榧（ほんかや）調将棋盤（天面木目、漆目罫線、木口側面ブロック、上部リムライト）
- 盤幅・盤高 3/9・6/9 対称位置（7三・4三・7六・4六）の4つの星印
- 表示専用モードでのアクセシビリティ対応（81マスの不要なTab停止ゼロ化）
- 対局・操作モードでの roving tabindex キーボード操作（矢印キー移動、Enter/Space決定）
- スクリーンリーダー対応（先手王将・後手玉将・成駒・空マスの正確なARIA読み上げ）
- **将棋ドメイン層・合法手エンジン**:
  - 盤面上の全駒（歩・香・桂・銀・金・角・飛・王/玉・成駒各種）の幾何学的利き・移動候補計算
  - 王手判定（`isKingInCheck`）および自玉の安全確認（王手放置・ピンされた駒の離脱・自殺手の禁止）
  - **一般的な詰み判定と終局処理**:
    - `isPlayerInCheck` / `hasLegalBoardMove` / `hasLegalDrop` / `hasLegalResponse` / `isCheckmate` による純粋な局面照会
    - 玉の退避、王手駒の捕獲、盤上移動・駒打ちによる合駒、成り・不成を含む全合法応手の探索
    - 通常移動・成り・突き歩・歩以外の駒打ちによる詰みを `checkmate` として終局し、勝者・敗者・最終着手を記録
    - 応手がある王手は `status: 'check'`、王手でない局面は `status: 'active'` として共通更新
    - 王手中の手番と、詰みによる勝者をステータスバッジで文字表示し、終局後の盤・駒台・成り選択を無効化
  - **千日手・連続王手の千日手**:
    - 盤上の全駒の位置・所有者・駒種・成り状態、先後別・駒種別の持ち駒枚数、次の手番がすべて一致する局面を同一局面と定義
    - 駒の個体ID、持ち駒配列の順序、手数、棋譜・反則履歴、直前手、状態・結果などのメタデータは局面比較から除外
    - 固定順の盤面配列と正規化した持ち駒枚数から `createPositionKey` が決定的な局面キーを生成し、初期局面と各合法手後の局面を小さな `positionHistory` に記録
    - 同一局面の4回目で通常の千日手を `repetition` として終局し、勝者・敗者のない無勝負として記録・表示
    - 4出現の1回目直後から4回目までに一方の全着手が王手だった場合は、`perpetual_check_repetition` による王手側の反則負けとして記録・表示
    - 通常移動と駒打ち、assist方式とstrict方式のどちらも共通終局処理を使用。外部から渡されたカスタム局面の履歴が不一致なら現在局面を新しい基準として安全に再初期化
    - 千日手成立後に先後を交代して自動的に指し直す機能は未実装（現在は一局を無勝負として終了）
  - 成駒の移動ルール（と金・成香・成桂・成銀＝金将の動き、竜王＝飛車＋斜め1マス、竜馬＝角＋縦横1マス）
  - 行き所のない駒（`dead_piece`）の判定（1/9段目の歩・香、1/2段目・8/9段目の桂馬）
  - 指し手検証API（`validateMove`）による不正理由の詳細識別（盤外、手番違反、王手放置、自殺手等）
  - 成り・不成の選択ダイアログと、歩・香・桂の必須成り
  - **基本的な駒打ち**:
    - 持ち駒を `Piece.id` で選択し、合法な空きマスへ1枚だけ配置
    - `validateDrop` / `getLegalDropSquares` / `simulateDropSquares` / `executeDrop` による検証・候補生成・仮想盤面・局面更新
    - 先手・後手の行き所のない駒打ち、同じ筋の未成歩だけを数える二歩、駒打ち後の王手放置を拒否
    - 飛車・角・香の直線王手に対する合駒、駒打ちによる相手玉への王手に対応
    - 歩打ち後の仮想盤面と相手側の合法な盤上移動を用いた打ち歩詰め判定（`pawn_drop_mate`）
    - 通常移動と駒打ちを `kind: 'move' | 'drop'` で履歴上区別し、駒打ち棋譜を `▲5五歩打` の形式で記録
  - **公開APIの統制と低レベル盤面更新処理のカプセル化**:
    - 盤上移動は `executeMove`（および後方互換の `applyMove`）、駒打ちは `executeDrop` を外部向け着手APIとして公開。
    - 駒打ちの事前確認には `validateDrop` と `getLegalDropSquares`、王手放置判定用の仮想盤面には `simulateDropSquares` を公開。
    - 検証を通さない低レベル盤面更新関数（`internalApplyLegalMove`）は内部専用（非公開）とし、検証回避による不正手適用経路を完全排除。
  - **提案元（proposer）に応じた既定モードの自動選択**:
    - `proposer: 'human'`（または省略時）: **アシスト方式（`assist`）**（禁じ手を候補から除外・安全に拒否し対局継続）
    - `proposer: 'local_ai'` / `'shogi_engine'`: **厳格対局方式（`strict`）**（禁じ手を提案手として受け取り、盤面・手番・手数を変更せず反則負け `foul_loss` として記録）
    - `mode` が明示された場合は明示値を優先。
  - **反則履歴（`FoulRecord`）の厳密記録**:
    - 移動元に実在する駒がある場合のみ駒種を記録。移動元が空マスや盤外など特定不能な場合は `pieceType: null` を記録（架空の駒種補完を排除）。
  - **終局後の着手拒否**:
    - 終局済み（`status: 'ended'`）の局面に対する着手は、専用理由コード `game_already_ended` で安全に拒否（新規反則負けの生成や状態破壊を防止）。
  - 内部でのイミュータブルな局面更新、手番交代、手数加算、駒捕獲（成駒の成解除）、棋譜生成（`▲7六歩`等）
- Node.js 24系＋npmに統一された厳格な依存関係・ロックファイル管理とクロスプラットフォームクリーン処理

## セットアップ手順

1. **Node.js バージョンの確認**
   ```bash
   node --version
   ```
   ※ 出力が `v24.15.0` 未満の場合は、Node.js 24.19.0 LTS に更新してください（nvm 等をご利用の場合は `nvm use` を実行）。

2. **npm バージョンの確認**
   ```bash
   npm --version
   ```

3. **依存パッケージのクリーンインストール**
   `package-lock.json` に基づき、厳密なインストールを実行します：
   ```bash
   npm ci
   ```

4. **一括検証（ロックファイル・型・テスト・ビルド）**
   ```bash
   npm run check
   ```

5. **開発サーバー起動**
   ローカル開発サーバー（ポート3000）を起動：
   ```bash
   npm run dev
   ```

## 依存パッケージの install script 審査（セキュリティ方針）

npm 11.17 以降のセキュアなスクリプト実行制御に準拠し、依存パッケージの install script を明示的に審査・管理しています：

- **許可・拒否の個別管理**: `package.json` の `allowScripts` フィールドで各パッケージのスクリプト実行許可（`true`）／拒否（`false`）を個別に指定します：
  - `esbuild`: `true`（Vite・テスト・ビルドに必要なバイナリインストーラー）
  - `@google/genai`: `false`（不要な no-op スクリプト）
  - `protobufjs`: `false`（非推奨警告メッセージ表示のみ）
  - `fsevents`: `false`（`fsevents@2.3.3` は pre-built の `fsevents.node` バイナリを同梱して配布しているため、`node-gyp rebuild` を拒否した状態でもモジュール読み込みが可能であり、独立した macOS CI 検証スクリプトにおいてネイティブ監視および Vite watcher の動作を継続検証しています）
- **未審査スクリプトの遮断**: `.npmrc` に `strict-allow-scripts=true` を設定しているため、`allowScripts` に記載のない未審査のスクリプトが存在する場合、`npm ci` / `npm install` はエラーとなり実行が停止します。
- **新しい依存関係追加時の運用**: 新たにパッケージを追加・更新する際は、必ず install script（`preinstall`, `install`, `postinstall`）の有無と処理内容を確認し、真にビルドや動作に不可欠なもののみを許可してください（安易に全スクリプトを許可したり `--dangerously-allow-all-scripts` を使用しないこと）。

## CI / CD
GitHub Actions（`.github/workflows/ci.yml`）により、main/master ブランチへの push、pull request、および手動実行（`workflow_dispatch`）時に、Linux（`ubuntu-latest`）および macOS（`macos-latest`）の両 OS 環境において Node.js `24.19.0` 上で以下の一貫したパイプラインが自動実行されます：
- `npm ci`（依存関係インストール・スクリプト遮断検証）
- `npm run verify:lock`（ロックファイル完全性検証・欠落集計）
- `npm run verify:macos-fsevents`（macOS環境でのみ実行: 独立した Node.js プロセスによる `fsevents` ネイティブ監視・Vite watcher 動作確認）
- `npm run lint`（TypeScript 型チェック）
- `npm test`（Vitest テストスイート）
- `npm run build`（本番ビルド）
